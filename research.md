# One IR powers three Penpot code emitters

All sources were checked on 2026-10-20 unless a different date is given. Every fact carries its primary source inline. Facts backed only by secondary sources (blogs, forums, search snippets, third-party listings), and facts the researchers took from prior knowledge without re-checking them, are marked **unverified**. Sentences labelled *Inference* or *Recommendation* are this report's reasoning, not sourced facts.

Penpot designs can be turned into Slint, SwiftUI and WinUI 3 XAML by three separate Penpot plugins that share one TypeScript core. Penpot's Plugin API (`@penpot/plugin-types` 1.5.0 on the npm `next` tag) exposes the shape tree with explicit flex and grid layout, per-child sizing, constraints, fills, strokes, shadows, styled text runs, components, variants and resolved design tokens ([plugin-types 1.5.0](https://unpkg.com/@penpot/plugin-types@1.5.0/index.d.ts)). A shared intermediate representation (IR) can therefore be built from structure rather than from CSS. Two adapters feed it: one reads the live Plugin API, the other reads the `.penpot` binfile v3 (a ZIP of JSON) for a headless CLI. One pure emitter per target turns the IR into files plus a fidelity report. No Penpot plugin for Slint, SwiftUI or WinUI exists today, so this family would be first of its kind ([GitHub search](https://github.com/search?q=penpot+swiftui&type=repositories)). Claude Design has **no public API, MCP server or deep link** ([Claude API overview](https://platform.claude.com/docs/en/api/overview)), and Anthropic's Consumer Terms forbid automating claude.ai without an API key ([Consumer Terms](https://www.anthropic.com/legal/consumer-terms)). The Claude Design plugin can therefore only prepare a handoff bundle that the user carries into Claude Design. The "select, prompt, redesign" loop belongs on the Claude Messages API, with model output sanitized and inserted as a new board. For the desktop version, Electron beats Tauri because it ships Chromium, Penpot's best-supported engine, which matters as Penpot moves to a WASM, Skia and WebGL renderer. The only mature prior art, author-more/penpot-desktop, is AGPL-3.0, so it can be studied but not copied ([penpot-desktop package.json](https://github.com/author-more/penpot-desktop/blob/main/package.json)).

## Penpot's 1.5.0 plugin API exposes enough structure for native codegen

A Penpot plugin has two halves. **Plugin code runs in an SES compartment** with the `penpot` global, timers, hardened intrinsics and a `fetch` wrapper. That `fetch` forces `credentials: 'omit'`, blanks the `Authorization` header and exposes only `text()` and `json()`, so binary reads are impossible. Plugin code has no DOM, `window` or `document` ([create-sandbox.ts, develop](https://github.com/penpot/penpot/blob/develop/plugins/libs/plugins-runtime/src/lib/create-sandbox.ts)). **The UI half is an iframe served from the plugin's own host.** The two halves talk through `penpot.ui.sendMessage`, `window.postMessage` and `penpot.ui.onMessage`, and the UI should check `event.source === window.parent` ([create-a-plugin.md, develop](https://github.com/penpot/penpot/blob/develop/docs/plugins/create-a-plugin.md)). The iframe sandbox always grants `allow-scripts`, `allow-same-origin`, `allow-forms`, `allow-modals` and `allow-popups`. It adds `allow-downloads` only when the manifest declares `allow:downloads`, and clipboard access only for the clipboard permissions ([plugin-modal.ts, develop](https://github.com/penpot/penpot/blob/develop/plugins/libs/plugins-runtime/src/lib/modal/plugin-modal.ts)). Penpot validates manifests with zod. The schema allows `content:read|write`, `library:read|write`, `user:read`, `comment:read|write`, `allow:downloads`, `allow:localstorage`, `clipboard:read|write`, and three unreleased management permissions plus `allow:global` ([manifest.schema.ts, develop](https://github.com/penpot/penpot/blob/develop/plugins/libs/plugins-runtime/src/lib/models/manifest.schema.ts)). With manifest `"version": 2`, relative `code` and `icon` paths resolve against the manifest URL, and since Penpot 2.17.0 validation errors throw by default ([create-a-plugin.md](https://github.com/penpot/penpot/blob/develop/docs/plugins/create-a-plugin.md), [CHANGES.md](https://github.com/penpot/penpot/blob/develop/CHANGES.md)). Distribution is just a manifest URL served with CORS headers, entered in the Plugin Manager (Ctrl+Alt+P) or listed on the Penpot Hub, which had **127 plugins** on the check date ([deployment.md](https://github.com/penpot/penpot/blob/develop/docs/plugins/deployment.md), [Penpot Hub](https://penpot.app/penpothub/plugins)).

Version choice matters. On npm, `latest` is **1.4.2** (2026-01-21) and `next` is **1.5.0** (2026-07-08). The current Penpot release is **2.18.3** (2026-10-06) ([npm registry](https://registry.npmjs.org/@penpot/plugin-types), [GitHub releases API](https://api.github.com/repos/penpot/penpot/releases)). The token interfaces (`TokenCatalog`, `TokenSet`, `TokenTheme`, typed tokens with `value` and `resolvedValue`) **first appear in 1.5.0**, and 1.5.0 also fixed container sizing typed as `'fit-content'` to `'fix'` ([1.4.2 d.ts](https://unpkg.com/@penpot/plugin-types@1.4.2/index.d.ts) vs [1.5.0 d.ts](https://unpkg.com/@penpot/plugin-types@1.5.0/index.d.ts), [plugins CHANGELOG](https://github.com/penpot/penpot/blob/develop/plugins/CHANGELOG.md)). Penpot 2.17.0 and 2.18.0 carry dozens of Plugin API fixes (read-only fill arrays, wrong-page creation, token application, whole-page export). Unreleased 2.19.0 fixes missing permission checks and a postMessage channel that broadcast to all plugins without origin validation ([CHANGES.md](https://github.com/penpot/penpot/blob/develop/CHANGES.md)). *Recommendation:* pin `@penpot/plugin-types@1.5.0` and test against Penpot 2.17 or later.

The data a converter needs is all typed. `Shape` is the union `Board | Group | Boolean | Rectangle | Path | Text | Ellipse | SvgRaw | Image`, and `Image` is deprecated in favour of `Fill.fillImage`. Boards carry `clipContent`, optional `flex` (direction, wrap) and `grid` (row and column `Track[]`), and container sizing. Layout children carry `absolute`, `zIndex`, `horizontalSizing`/`verticalSizing` (`auto|fill|fix`), `alignSelf`, margins and min/max sizes. Grid cells carry row, column, spans, area name and placement mode. Every shape also exposes constraints, per-corner radii, `fills` (which can read `'mixed'`), strokes with alignment and style, shadows, `blur`, `backgroundBlur`, `blendMode`, rotation and flips, plus `tokens` keyed by token name ([plugin-types 1.5.0](https://unpkg.com/@penpot/plugin-types@1.5.0/index.d.ts)). In 1.4.2, `Track.type` is `'flex' | 'fixed' | 'percent' | 'auto'`, `Gradient.type` is only `'linear' | 'radial'` (with a `width` that sets the ellipse ratio), and there are **16 blend modes**. Stroke caps include arrows and markers ([plugin-types 1.4.2](https://unpkg.com/@penpot/plugin-types@1.4.2/index.d.ts)). Text exposes font id, family, variant, size, weight, style, line height, letter spacing, transform, decoration, direction, alignment and `growType`. `getRange(start, end)` returns styled runs, which is how mixed-style text must be walked ([plugin-types 1.5.0](https://unpkg.com/@penpot/plugin-types@1.5.0/index.d.ts)). The variants API arrived in plugins 1.4.0 ([plugins CHANGELOG](https://github.com/penpot/penpot/blob/develop/plugins/CHANGELOG.md)).

Penpot also ships helpers, but they are web-only. `generateMarkup` produces HTML or SVG, `generateStyle` produces CSS, and `generateFontFaces` produces `@font-face` rules. `shape.export({type: 'png'|'jpeg'|'webp'|'svg'|'pdf', scale, skipChildren})` resolves to a `Uint8Array`, and so does `penpot.currentFile.export('penpot'|'zip', 'all'|'merge'|'detach')`, which has existed since plugin-types 0.10.0 ([plugin-types 1.5.0](https://unpkg.com/@penpot/plugin-types@1.5.0/index.d.ts), [0.10.0](https://unpkg.com/@penpot/plugin-types@0.10.0/index.d.ts)). In the frontend, `'penpot'` becomes binfile v3 only when the `export-file-v3` flag is on, otherwise binfile v1 ([file.cljs, develop](https://github.com/penpot/penpot/blob/develop/frontend/src/app/plugins/file.cljs)). Binfile v3 is a ZIP with `manifest.json`, `files/{id}.json`, per-page and per-shape JSON, `media/`, `colors/`, `components/`, `typographies/`, `tokens.json` and binary objects. Its fields use storage names (`frame`, `rect`, `circle`, `r1`–`r4`, `constraintsH`, `appliedTokens`, `shapeRef`) rather than Plugin API names ([penpot-file-format.md, develop](https://github.com/penpot/penpot/blob/develop/docs/technical-guide/developer/data-model/penpot-file-format.md)). `@penpot/library` 1.2.0 (MPL-2.0) only *builds* such files; its README documents no read API ([library README](https://github.com/penpot/penpot/blob/develop/library/README.md), [npm](https://registry.npmjs.org/@penpot/library)). For headless use, the backend RPC exposes `get-file` and `export-binfile` behind personal access tokens sent as `Authorization: Token <token>` ([integration guide](https://help.penpot.app/technical-guide/integration/), [binfile.clj](https://github.com/penpot/penpot/blob/develop/backend/src/app/rpc/commands/binfile.clj)). The exact response format of `export-binfile` was not verified.

The existing ecosystem leaves the native lane empty. Catalog code exporters target HTML, Tailwind and web frameworks (Tailwind HTML, Code Layers, Locofy); penpot2flutter targets Flutter (catalog only, **unverified**). Token exporters reach SwiftUI and Compose only for tokens ([Penpot Hub](https://penpot.app/penpothub/plugins), [Locofy listing](https://penpot.app/penpothub/plugins/locofy)). GitHub searches for "penpot swiftui", "penpot slint", "penpot xaml" and "penpot winui" returned nothing ([GitHub search](https://github.com/search?q=penpot+slint&type=repositories)). Only the first 32 of 127 catalog entries were inspected, so the "first of its kind" claim is strong but not exhaustive.

## A shared IR with two adapters and one emitter per target

The architecture follows from three constraints. Plugin code has the data but no DOM. The UI iframe has the DOM, `Blob` and downloads but no `penpot`. And the same conversion must also run headless from a `.penpot` file. Penpot's own plugins live in a pnpm workspace with `apps/` and `libs/` ([penpot/penpot plugins/](https://github.com/penpot/penpot/tree/develop/plugins)), and the official starter template uses Vite and TypeScript with separate `plugin.ts` and `index.html` entries ([starter template](https://github.com/penpot/penpot-plugin-starter-template)). *Recommendation:* use a pnpm monorepo with the following packages.

| Package | Role | Runs in |
| --- | --- | --- |
| `packages/ir` | Pure TypeScript types plus a zod schema for the node tree: identity, geometry, layout (none/flex/grid with tracks), child sizing and constraints, paint stacks (fills, strokes with alignment and dash, effects), text runs, asset refs, token refs, component and variant refs | Anywhere |
| `packages/adapter-plugin-api` | Penpot `Shape` → IR. Normalizes `'mixed'`, walks `getRange` runs, reads `tokens`, resolves library refs, collects asset export requests | Plugin code (SES, no DOM) |
| `packages/adapter-binfile` | `.penpot` ZIP → IR. Sniffs v1 vs v3, maps storage names, resolves `appliedTokens` against `tokens.json`, enforces entry-count and size caps | Node CLI, desktop, UI iframe |
| `packages/passes` | Shared IR → IR passes: hidden-layer pruning, multi-fill stacking, outer-stroke inflation, absolute-in-flex wrapping, reverse-direction reordering, group flattening, each with a target capability flag | Anywhere |
| `packages/emit-slint`, `emit-swiftui`, `emit-winui` | Pure `(IR, options) → { files: Map<path, string|bytes>, warnings[] }` | Anywhere |
| `packages/emit-ai-bundle` | IR plus exports → Claude handoff bundle and API payload | UI iframe, desktop |
| `packages/plugin-shell` | Shared UI, typed message protocol, asset transfer, zip/download, theming via `@penpot/plugin-styles` | UI iframe |
| `apps/plugin-slint`, `plugin-swiftui`, `plugin-winui`, `plugin-claude` | Thin apps: own `manifest.json` (v2), icon and Vite config | Penpot |
| `apps/cli` | `penpot file or RPC → binfile adapter → emitter` | Node |
| `apps/desktop` (optional) | Electron shell that serves the plugins and adds native capabilities | Electron |

*Inference:* the adapter must run in plugin code, because only there can it read shapes and call `shape.export` for image and SVG bytes. The resulting IR and `Uint8Array` assets cross to the UI iframe by structured clone. Emitters and ZIP packaging then run in the iframe, which can build a `Blob` and trigger a download under `allow:downloads`. Nobody has tested the claim that typed arrays survive `penpot.ui.sendMessage`; it is an inference from postMessage semantics. The plugin-code bundle must be a single self-contained script with no dynamic imports, because SES evaluates one code string. Each converter manifest needs only `content:read`, `library:read` and `allow:downloads`. The Claude plugin adds `content:write` for write-back.

The IR is the product, so three design rules are worth fixing early. First, **the IR records what the designer meant, not how one target renders it**. Penpot gives explicit flex and grid semantics, so unlike FigmaToCode, which has to infer auto layout for free-positioned frames, the core never needs to guess layout for laid-out boards ([FigmaToCode](https://github.com/bernaferrari/FigmaToCode)). Second, **every emitter returns warnings as data**. A fidelity report listing blur, blend modes, dashes, outer strokes, elliptical gradients, per-span typography and grid tracks is what separates an honest converter from a silent one. FigmaToCode does the same, flattening mixed text to its first segment and emitting only the first shadow ([swiftuiTextBuilder.ts](https://github.com/bernaferrari/FigmaToCode/blob/HEAD/packages/backend/src/swiftui/swiftuiTextBuilder.ts), [swiftuiEffects.ts](https://github.com/bernaferrari/FigmaToCode/blob/HEAD/packages/backend/src/swiftui/builderImpl/swiftuiEffects.ts)). Third, **tokens and components are first-class IR nodes**, so each emitter can write a variable reference instead of a literal and an instance call instead of inlined geometry. Figma's own SwiftUI guidance prefers project tokens such as `Color.brandPrimary` over hex literals ([figma/mcp-server-guide design-to-code.md](https://github.com/figma/mcp-server-guide/blob/HEAD/skills/figma-swiftui/references/design-to-code.md)).

An optional second stage can use an LLM, which is what Figma's `figma-swiftui` skill does. It treats generated React and Tailwind as "a structural reference, not output", maps structures to `List`, `Form`, `TabView` and `Toggle`, drops device chrome, and treats the screenshot as the source of truth ([figma-swiftui design-to-code.md](https://github.com/figma/mcp-server-guide/blob/HEAD/skills/figma-swiftui/references/design-to-code.md)). *Recommendation:* keep deterministic emission as the baseline and add semantic control recognition later as an opt-in pass through the same Claude API path described below.

## Mapping tables: where each target loses fidelity

### Slint 1.18.1: strong layout, weak effects

Slint 1.18.1 (2026-09-21) is current; 1.19.0 is in nightly ([crates.io](https://crates.io/api/v1/crates/slint), [npm slint-ui](https://registry.npmjs.org/slint-ui)). Release 1.18 added `FlexboxLayout` with wrapping and per-item `cross-axis-self-alignment`, plus `line-height-factor`, `max-lines` and struct field defaults ([CHANGELOG v1.18.1](https://github.com/slint-ui/slint/blob/v1.18.1/CHANGELOG.md)). *Recommendation:* emit for Slint 1.18 or later. Use `HorizontalLayout`/`VerticalLayout` for single-line flex, which the docs call simpler and faster, and reserve `FlexboxLayout` for wrapping or reversed directions ([FlexboxLayout docs](https://docs.slint.dev/latest/docs/slint/reference/layouts/flexboxlayout/)). The docs.slint.dev "latest" pages label themselves as next-version docs, so key properties were cross-checked against the v1.18.1 CHANGELOG.

| Penpot | Slint | Fidelity |
| --- | --- | --- |
| Board, rect | `Rectangle` with `background`, `border-*`, per-corner radii, `clip: true` for clip content | Good ([Rectangle](https://docs.slint.dev/latest/docs/slint/reference/elements/rectangle/)) |
| Ellipse | Circle as `Rectangle` with radius `width/2`; true ellipse as `Path` arcs | *Inference*: no Ellipse element is documented |
| Path, boolean | `Path { commands: "<svg d>"; fill-rule; stroke }` | Booleans must be pre-flattened; no dash or stroke alignment ([Path](https://docs.slint.dev/latest/docs/slint/reference/elements/path/)) |
| Image fill | `Image { source: @image-url(...); image-fit }` | `@image-url` is a compile-time literal, so assets go beside the file or into `data:` URIs ([images.mdx](https://github.com/slint-ui/slint/blob/v1.18.1/docs/astro/src/content/docs/reference/property-types/images.mdx)) |
| Flex direction, gap, padding, wrap | H/V layouts or `FlexboxLayout`, `spacing-*`, `padding-*` | Good; mind the row/column gap axes |
| Justify, align-items, align-content, align-self | `alignment`, `cross-axis-alignment`, `cross-axis-line-alignment`, `cross-axis-self-alignment` | Good since 1.18 |
| Child sizing fix / hug / fill | `width`/`height`; omit size; `*-stretch: 1` plus container `alignment: stretch` | Partial: no flex-shrink control |

| Constraints | Bindings to `parent.width`/`parent.height` | *Inference*: no constraint property, but bindings express every kind |
| Rotation, opacity, hidden | `transform-rotation`, `opacity`, `visible` | Good ([common.mdx](https://github.com/slint-ui/slint/blob/v1.18.1/docs/astro/src/content/docs/reference/common.mdx)) |
| Linear and radial gradients | `@linear-gradient`, `@radial-gradient(circle ...)` | **Lossy**: circle only, no elliptical radial ([colors-and-brushes.mdx](https://github.com/slint-ui/slint/blob/v1.18.1/docs/astro/src/content/docs/reference/property-types/colors-and-brushes.mdx)) |
| Multiple fills or strokes | Stacked sibling Rectangles | *Inference*: `background` is one brush |
| Stroke inside / center / outside | `border-*` (inside, **unverified**) / Path stroke / inflated outer Rectangle | Outer is emulated; no stroke-alignment property |
| Dashed or dotted stroke | None | **Unsupported** |
| Drop shadow | `drop-shadow-*` | One per element; spread is Skia only |
| Inner shadow | `inner-shadow-*` | **Skia renderer only** (1.17) |
| Layer blur, background blur, blend modes | None | **Unsupported**: rasterize or warn ([common.mdx](https://github.com/slint-ui/slint/blob/v1.18.1/docs/astro/src/content/docs/reference/common.mdx)) |
| Masks | `clip: true` | Rect and rounded-rect only; other masks need rasterizing (*inference*) |
| Single-style text | `Text` with family, size, weight, italic, `letter-spacing`, `line-height-factor`, wrap, alignment | Good, but no underline, strikethrough or text-transform ([Text](https://docs.slint.dev/latest/docs/slint/reference/elements/text/)) |
| Mixed-style text | `StyledText { text: @markdown(...) }` | **Lossy**: italic, strike, `<u>`, `<font color>` and links only; no per-span size, family or letter spacing ([StyledText](https://docs.slint.dev/latest/docs/slint/reference/elements/styledtext/)) |
| Fonts | `import "./font.ttf";` | Good: .ttf, .ttc, .otf ([fonts.mdx](https://github.com/slint-ui/slint/blob/v1.18.1/docs/astro/src/content/docs/guide/development/fonts.mdx)) |

Tokens map to `export global` singletons ([globals.mdx](https://github.com/slint-ui/slint/blob/v1.18.1/docs/astro/src/content/docs/guide/language/coding/globals.mdx)). Slint's own MIT-licensed Figma inspector already emits one global per variable collection, plus a `Mode` enum and a `current` scheme when there are several modes, referenced as `Colors.current.primary` ([export-variables.ts](https://github.com/slint-ui/slint/blob/v1.18.1/tools/figma-inspector/backend/utils/export-variables.ts)). *Recommendation:* mirror that pattern for Penpot token themes and sets so the output feels native to Slint users. Typography tokens become structs with field defaults (1.18). Main components become `export component X inherits Rectangle` with `in property` declarations for overridable text, visibility and images. Variants become an `in property` enum with `states` or ternary bindings, or separate components when their structure differs.

### SwiftUI: near-complete paint coverage, layout needs helpers

Apple's DocC availability data supports a default target of **iOS 17 / macOS 14**. On that floor, `strokeBorder(_:style:)` gives inner strokes, `UnevenRoundedRectangle` gives per-corner radii, `Grid` and the `Layout` protocol are available, and `containerRelativeFrame` handles percent sizing. True line height (`lineHeight(_:)` and `AttributedString.LineHeight`) needs **iOS 26 / macOS 26** ([lineHeight](https://developer.apple.com/documentation/swiftui/view/lineheight(_:)), [AttributedString.LineHeight](https://developer.apple.com/documentation/foundation/attributedstring/lineheight)). The 2026 SwiftUI release (iOS 27, Xcode 27) adds toolbar, document and `ArrangementView` APIs but **no new primitive layout tool** such as a flow layout ([WWDC26 SwiftUI guide](https://developer.apple.com/wwdc26/guides/swiftui/), [SwiftUI updates](https://developer.apple.com/documentation/updates/swiftui)). Generated code should avoid the deprecated `cornerRadius(_:antialiased:)` modifier and the `Text +` operator ([cornerRadius](https://developer.apple.com/documentation/swiftui/view/cornerradius(_:antialiased:)), [Text +](https://developer.apple.com/documentation/swiftui/text/+(_:_:))).

Fonts are the main trap. `Font.custom` must use the **PostScript name**, and SwiftUI silently falls back to the system font when it cannot load the font. It also does not synthesize bold or italic for custom fonts. Font files must be listed in `UIAppFonts` (iOS) or `ATSApplicationFontsPath` (macOS) ([Applying custom fonts](https://developer.apple.com/documentation/swiftui/applying-custom-fonts-to-text)), or registered at runtime with `CTFontManagerRegisterFontsForURL` when they ship in a Swift package ([CTFontManagerRegisterFontsForURL](https://developer.apple.com/documentation/coretext/ctfontmanagerregisterfontsforurl(_:_:_:))). FigmaToCode emits family names, which can fall back silently ([swiftuiTextBuilder.ts](https://github.com/bernaferrari/FigmaToCode/blob/HEAD/packages/backend/src/swiftui/swiftuiTextBuilder.ts)). *Recommendation:* resolve PostScript names from font metadata or the font file's `name` table. Colors map to `Assets.xcassets/<Name>.colorset/Contents.json`, whose documented schema dates from 2018 and omits the dark-mode `appearances` key ([Named Color Type](https://developer.apple.com/library/archive/documentation/Xcode/Reference/xcode_ref-Asset_Catalog_Format/Named_Color.html)). Components become `struct X: View` with stored properties, variants become Swift enums switched in `body`, and typography becomes `extension Font` statics (*inference*).

## Validation runs where each toolchain actually lives

Each target needs layered validation. The same tiers also satisfy the workspace rule that every task ships with a test. The **shared tier** is target-independent. It uses fixture `.penpot` files fed through the binfile adapter, IR schema validation with zod, and snapshot tests of emitter output in Vitest. Slint's MIT-licensed Figma inspector tests against exported Figma JSON fixtures the same way ([figma-inspector](https://github.com/slint-ui/slint/tree/v1.18.1/tools/figma-inspector)). Visual regression compares Penpot's own `shape.export` PNG against a render of the generated code.

**Slint** is the easiest. `slint-viewer --check file.slint` prints diagnostics and exits 1 on error, and `--screenshot out.png` renders headlessly. Viewer, compiler and LSP binaries ship for macOS arm64, Linux and Windows with every release ([slint-viewer.mdx](https://github.com/slint-ui/slint/blob/v1.18.1/docs/astro/src/content/docs/guide/tooling/slint-viewer.mdx), [release v1.18.1](https://github.com/slint-ui/slint/releases/tag/v1.18.1)), so a Linux CI job can check and pixel-diff every fixture. An in-plugin live preview is technically possible through `slint-wasm-interpreter`, which exposes `compile_from_string` with diagnostics and canvas rendering. However, that crate has `publish = false` and is not on npm, so the plugin would have to build and vendor its own WASM ([wasm-interpreter](https://github.com/slint-ui/slint/tree/v1.18.1/api/wasm-interpreter)). The licensing problem below makes this optional at best.

**SwiftUI** cannot be type-checked or rendered off Apple platforms. In the browser, the emitter should be syntactically valid by construction, built from a typed builder rather than string templates, and snapshot-tested. Compiling swift-syntax to WASM with the official Swift WASM SDKs (official since Swift 6.2; the guide uses 6.4.1) could add syntax diagnostics, but feasibility and size are **unverified** ([swift.org WASM guide](https://www.swift.org/documentation/articles/wasm-getting-started.html)). Real checks run on a macOS arm64 CI runner or the desktop app on a Mac: `swift format lint`, which errors on unparsable files ([swift-format](https://github.com/swiftlang/swift-format)), then `swiftc -typecheck` against the iOS simulator SDK at the chosen deployment target. That command is an *inference* from standard flags and was not run. For humans, the plugin exports a SwiftPM package with `#Preview` blocks ([Preview macro](https://developer.apple.com/documentation/swiftui/preview(_:body:))), an asset catalog, fonts and a registration helper.

**WinUI** splits the same way. The browser tier is a DOMParser well-formedness check plus an allow-list of element and property names generated offline from WinUI metadata. No official XAML schema was found. The approximate preview tier is a self-hosted Uno Platform WASM app calling its runtime `XamlReader` ([Uno Markup sources](https://github.com/unoplatform/uno/tree/master/src/Uno.UI/UI/Xaml/Markup), [Uno Playground](https://playground.platform.uno/)). It renders through Skia, so expect structural rather than pixel fidelity, and nobody has checked whether it supports `ThemeResource`, toolkit types or `ms-appx` fonts. The exact tier is a WinAppSDK project built on a Windows CI runner or on a Windows desktop install.

## Claude Design has no programmatic door; the Claude API is the working fallback

**Verdict: a Penpot plugin cannot drive Claude Design.** Claude Design launched on 2026-04-17 as an Anthropic Labs research preview ([Anthropic news](https://www.anthropic.com/news/claude-design-anthropic-labs)). Since September 2026 it has been an artifact type inside ordinary Claude conversations, the Artifacts tab and Claude Code (`/design`, `/design-sync`) ([Claude blog](https://claude.com/blog/claude-design-stays-on-brand-for-daily-work)). It is included in every plan, Free included, and the standalone claude.ai/design closes on 2026-12-14 ([claude.com/design](https://claude.com/design), [Help: migrate](https://support.claude.com/en/articles/17440474-migrate-from-standalone-claude-design-to-claude)). The Claude API lists Messages, Batches, Token Counting, Models, Files and Skills, plus beta Agents, Sessions and Environments, and **no Design endpoint** ([API overview](https://platform.claude.com/docs/en/api/overview)). The launch post promised integrations without describing any, and a Replit testimonial mentions a "Claude Design MCP integration" without setup documentation ([Anthropic news](https://www.anthropic.com/news/claude-design-anthropic-labs), [claude.com/design](https://claude.com/design)). No documented deep link with a prefilled prompt was found. The Consumer Terms prohibit accessing the services "through automated or non-human means" except via an API key ([Consumer Terms](https://www.anthropic.com/legal/consumer-terms)), so a plugin that reused a claude.ai browser session would breach them.

Claude Design also cannot read Penpot files. Its documented inputs are prompts, images, DOCX, PPTX and XLSX, PDF and PPTX as brand references, codebases and GitHub repos, and "design files" (Figma is the named example). The help centre lists no SVG, HTML or Penpot format, and React is the only framework it mentions ([Help: design system](https://support.claude.com/en/articles/14604397-set-up-your-design-system-in-claude-design), [Help: get started](https://support.claude.com/en/articles/14604416-get-started-with-claude-design)). Its exports are a .zip project archive, PDF, PPTX, Google Slides, standalone HTML, partner connectors (Canva, Adobe, Gamma, Lovable, Miro, Replit, Vercel, Wix and others, but not Penpot) and a handoff to Claude Code ([Help: get started](https://support.claude.com/en/articles/14604416-get-started-with-claude-design)). The handoff bundle's schema is not publicly documented.

*Recommendation:* the `plugin-claude` app should offer two clearly separated modes.

**Mode 1, "Hand off to Claude Design" (user-mediated).** The plugin exports the whole file with `currentFile.export('penpot')` for archival and round-trip. For the current selection it adds PNG (kept at or under 2576 px on the long edge) and PDF exports, `generateMarkup` HTML and SVG with `generateStyle` CSS, a tokens JSON derived from the IR, and a `prompt.md` holding the user's instruction. It downloads all of this as one ZIP (`allow:downloads`), optionally copies the prompt to the clipboard (`clipboard:write`, Penpot 2.16+), and opens Claude in a new tab, which `allow-popups` permits. The user uploads the PNG, PDF and HTML into a Design conversation. The `.penpot` file itself is not a documented Claude Design input, so it travels only as an archive. To come back, the user exports standalone HTML or the .zip from Claude Design and drops it into the plugin. The plugin can then import simple SVG through `createShapeFromSvgWithImages`, accepting a lossy round-trip ([plugin-types 1.4.2](https://unpkg.com/@penpot/plugin-types@1.4.2/index.d.ts)). Whether Claude Design accepts SVG or HTML uploads is unknown, so PNG and PDF are the safe carriers.

**Mode 2, "Redesign selection with Claude" (automated, ToS-clean).** This mode uses the Messages API with an API key. The plugin reads `penpot.selection`, builds the IR, and exports a PNG. It sends the image, a compact IR JSON or `generateMarkup` SVG, and the user's prompt. The model choice is `claude-opus-5-5` ($4/$20 per MTok) for quality or `claude-sonnet-5-5` ($2/$10) for cost, and both offer vision, tool use, a 1M context window and 128K output ([Models overview](https://platform.claude.com/docs/en/about-claude/models/overview)). The call forces a tool call whose input schema is a subset of the IR, falling back to SVG. Vision accepts JPEG, PNG, GIF and WebP (not SVG), up to 8000×8000 px and 10 MB per image, and Claude cannot output images, so the result must be text ([Vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)). The response is untrusted input. It must be validated against the IR zod schema, or the SVG must be sanitized by stripping scripts, `on*` handlers and external hrefs, under a size cap. The plugin then inserts the result as a **new board beside the original** through `createBoard`, `createText` and the other creation calls, or through `createShapeFromSvgWithImages`, and never replaces the selection in place. *Inference:* reusing the IR as the model's output schema means the adapter work pays twice. Only an IR-to-Penpot writer is new, and that writer also enables a future "import from code" direction.

API keys and network paths constrain where Mode 2 runs. The TypeScript SDK (`@anthropic-ai/sdk` 0.136.0) blocks browser use unless `dangerouslyAllowBrowser: true` is set, which adds the header `anthropic-dangerous-direct-browser-access: true` ([SDK client.ts](https://raw.githubusercontent.com/anthropics/anthropic-sdk-typescript/main/src/client.ts), [SDK README](https://github.com/anthropics/anthropic-sdk-typescript)). That is acceptable only for a user's own key held in memory, with a visible warning. The call belongs in the UI iframe, not in the SES `fetch`, because the SES wrapper blanks `Authorization` ([create-sandbox.ts](https://github.com/penpot/penpot/blob/develop/plugins/libs/plugins-runtime/src/lib/create-sandbox.ts)). Whether api.anthropic.com's CORS preflight succeeds from the plugin origin was not verified. A vendor key requires a server proxy with authentication and rate limits. In the desktop app the call moves to the main process, which removes CORS entirely.

Power users have a third option that needs no custom AI code. Penpot's official MCP server, in-app since 2.15.0 and on npm as `@penpot/mcp` 2.15.4 (stable) and 2.17.0 (next), lets Claude Code or Claude Desktop execute Plugin API code against the open file through a companion plugin ([docs/mcp/index.md](https://github.com/penpot/penpot/blob/develop/docs/mcp/index.md), [npm](https://registry.npmjs.org/@penpot/mcp)). It runs on the user's subscription and pairs naturally with `/design` in the same Claude Code session. It also runs arbitrary model-written code in the plugin context, needs a version-matched local server or the hosted remote mode, and requires the tab to stay active ([mcp README](https://github.com/penpot/penpot/tree/develop/mcp)). *Recommendation:* document it as the agentic path and keep the plugin's own Mode 2 as the in-canvas, deterministic path.

## Electron over Tauri for a desktop companion

Penpot has no official desktop app. The leading wrapper, author-more/penpot-desktop, is Electron (`^44.5.0`), **AGPL-3.0-or-later**, has 1,192 stars, and released v1.0.0 on 2026-09-30. It loads any Penpot instance in `<webview>` tabs with `persist:` partitions, DOM-patches Penpot through a webview preload, and runs the official Docker Compose stack through the `docker` CLI for local instances ([README](https://github.com/author-more/penpot-desktop/blob/main/README.md), [package.json](https://github.com/author-more/penpot-desktop/blob/main/package.json), [v1.0.0](https://github.com/author-more/penpot-desktop/releases/tag/v1.0.0)). It has no plugin-specific features. Every Tauri wrapper found has 0 or 1 stars ([GitHub search](https://github.com/search?q=penpot+desktop&type=repositories)). One search result, an unrelated "Windows utility … local helper for Penpot data folders", matches the fake-download lure pattern and must not be used.

**Recommendation: Electron.** Electron 44.9.2 is the current npm `latest`, and 45 was scheduled to go stable on the check date ([npm](https://registry.npmjs.org/electron), [schedule](https://releases.electronjs.org/schedule)). It bundles Chromium, while Penpot recommends the latest Chrome or Firefox and gives WebKit only "specific support" ([Penpot quickstart](https://help.penpot.app/user-guide/introduction/quickstart), search snippet, **unverified**). Penpot's renderer is moving to Rust and Skia compiled to WASM, with a WebGL render preference since 2.16 ([render-wasm README](https://github.com/penpot/penpot/blob/develop/render-wasm/README.md), [CHANGES.md](https://github.com/penpot/penpot/blob/develop/CHANGES.md)). Tauri 2.12.4 would run that renderer in WKWebView on macOS and WebKitGTK on Linux, tied to OS or distro versions ([Tauri webview versions](https://v2.tauri.app/reference/webview-versions/)). Its multi-webview `WebviewBuilder` also still requires the `unstable` feature ([docs.rs](https://docs.rs/tauri/latest/tauri/webview/struct.WebviewBuilder.html)). Tauri's genuine advantages, a smaller binary and direct Rust calls into Slint crates, are not decisive, because Electron can spawn `slint-viewer`, `swiftc` or `dotnet` as child processes. Nobody has tested Penpot's WebGL renderer under WKWebView, and that is the one finding that could reopen the choice.

*Recommendation, shell design:* use a `BaseWindow` with one `WebContentsView` per Penpot tab rather than the `<webview>` tag that Electron discourages. Keep `sandbox: true` and `contextIsolation: true` (both defaults), give each instance a `persist:` partition, and expose a minimal `contextBridge` preload ([webview-tag](https://www.electronjs.org/docs/latest/api/webview-tag), [WebContentsView](https://www.electronjs.org/docs/latest/api/web-contents-view), [WebPreferences](https://www.electronjs.org/docs/latest/api/structures/web-preferences)). The bundled plugins should stay byte-identical to the hosted ones and detect the bridge at runtime, falling back to browser downloads when it is absent.

Pre-installing plugins needs care. Penpot stores installed plugins **server-side in the user's profile props**, written via the `:add-profile-plugin` RPC ([register.cljs](https://github.com/penpot/penpot/blob/develop/frontend/src/app/plugins/register.cljs)). A plugin installed from the desktop app therefore appears in every browser session of that account. A custom-scheme manifest URL would break there, so a fixed `127.0.0.1` HTTP origin, or the public hosted manifests, is the safer choice. That RPC is internal and may change. The native bridge must never give Node to the plugin iframe. Either inject a narrow API only into frames whose origin is the app's own plugin origin, or relay postMessage through a page-level preload that validates with zod and forwards an allowlisted command set (`export-project(dir)`, `run-check(tool, dir)`, `claude.messages(...)`) to `ipcMain`. Raw shell strings must never pass, and folders are chosen through `dialog.showOpenDialog`. `session.on('will-download')` captures `.penpot` and ZIP exports straight into the chosen folder.

These native capabilities justify the desktop build:

| Capability | Mechanism |
| --- | --- |
| Write generated projects to disk | `will-download` or the bridge's `export-project`, without browser download dialogs |
| Run validators | `slint-viewer --check/--screenshot` on any OS; `swift format` and `swiftc -typecheck` on macOS; `dotnet build` on Windows; each a child process with fixed argv |
| Secure API key | `safeStorage` async API: Keychain on macOS, DPAPI on Windows, libsecret, kwallet or the Portal on Linux; refuse when Linux reports `basic_text` ([safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)) |
| Claude calls without CORS | Main process `@anthropic-ai/sdk`; the key never reaches renderers |
| Offline Penpot | Official compose stack (frontend on `localhost:9001`, backend, exporter, MCP, admin console, postgres 15, valkey 8.1, mailpit) driven through the `docker` CLI ([compose](https://github.com/penpot/penpot/blob/develop/docker/images/docker-compose.yaml)); on macOS run it under Colima |
| Local Penpot MCP | Prefer the compose `penpot-mcp` service or hosted remote MCP; if bundled, bind to 127.0.0.1 given the past "binding to all interfaces … unauthenticated RCE" fix ([CHANGES.md](https://github.com/penpot/penpot/blob/develop/CHANGES.md)) |

Distribution follows the workspace rules and Electron's guidance. macOS builds target arm64 only. They need signing and notarization, without which `safeStorage` keychain access and Squirrel.Mac auto-update become unreliable. Windows needs an EV certificate or Azure Artifact Signing to avoid SmartScreen warnings ([Electron code signing](https://www.electronjs.org/docs/latest/tutorial/code-signing)). Penpot publishes no trademark policy (`/trademark-policy` returns 404), and a third-party database lists PENPOT as registered to Kaleidos (**unverified**, [gleanmark](https://gleanmark.com/trademark/uspto-79378506)). *Recommendation:* ship under a distinct name described as "for Penpot", without Penpot logos unless Kaleidos approves.

The Slint licence needs a closer reading. A pure TypeScript emitter that writes `.slint` text and bundles no Slint runtime owes Slint nothing; the end user's app picks its own Slint licence. Embedding `slint-wasm-interpreter` for a live preview changes that. Under GPLv3 the plugin must be GPL-compatible open source. Royalty-free 2.0 forbids distributing Slint "alone and without integration into an Application", and forbids distributing an application "that exposes the APIs" of Slint ([Royalty-free 2.0](https://github.com/slint-ui/slint/blob/v1.18.1/LICENSES/LicenseRef-Slint-Royalty-free-2.0.md)). *Inference, not legal advice:* a plugin whose purpose is to compile arbitrary `.slint` sits close to the second clause. Either keep the preview out of the default build, make the plugin GPL-3.0, or ask SixtyFPS.

A fourth way is now planned: slint-bindings' own clean-room Slint compiler and interpreter, slintx, licensed Apache-2.0 with no Slint crate in its build (slint-bindings `plan.md` milestones M7a–M7c, tasks T73–T88; language research in slint-bindings `research.md` §8, 2026-10-20). Two of its parts serve this project: `slintx-syntax` (T73), a standalone parser that builds for WebAssembly and returns a syntax tree with spans and diagnostics, which could check emitter output in the plugin; and `slintx-web` (T85), the WebAssembly compiler, interpreter and WebGPU renderer for the live preview. Emitter fixtures from this project join slintx's conformance corpus (T74), so the M7b checkpoint is that they render like Slint does.

## Conclusion

The difficult part of this project is not reading Penpot, which exposes cleaner layout semantics than Figma, but defining the contract between a design intent and three runtimes with different gaps. Slint loses effects, SwiftUI loses layout conveniences, and WinUI loses effects and half its verified mapping surface. The fidelity report is therefore a core feature, and the IR is the most valuable asset, because it serves four consumers: three emitters and the Claude redesign loop's output schema. That loop also gives the project a reverse path from model output back into Penpot. The cheapest early wins are the Slint emitter, whose toolchain validates and screenshots on Linux CI, and the binfile CLI, which lets every emitter be snapshot-tested without a browser.

"Claude Design integration" should be framed honestly in the product. Today it is a user-carried handoff, not an API, and any plugin that automated claude.ai would breach Anthropic's terms. The automated experience users expect is delivered by the Messages API or by Penpot's own MCP server paired with Claude Code. If Anthropic ships the integrations its launch post promised, only Mode 1 of the Claude plugin needs to change. The desktop shell earns its place by doing what browsers cannot: running validators, writing project folders, holding the API key in the OS keychain, and hosting offline Penpot. It should stay an optional layer over plugins that work unchanged in any browser.
